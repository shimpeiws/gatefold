# Gatefold v0.5 scope and run-comparison contract

**Status: contract defined (v0.5, issue #44; implementation in #45–#48).**
The v0.5 CLI adds a `compare-traces` subcommand that explains an A → B
difference between two comparable runs by joining their yuurei `trace.json`
documents. This document defines the input, comparability, evidence, and
result contract. It is grounded in yuurei's public contract and trace schema
([yuurei trace contract](yuurei-trace-contract.md)) and in the v0.4
comparison contract ([v0.4 scope](v0.4-scope.md)). Gatefold still does not
execute yuurei, open a run directory, read a log, workspace, or artifact, or
read a path named inside a trace.

## CLI surface

v0.5 introduces one positional subcommand:

```text
gatefold compare-traces --before <A.trace.json|-> --after <B.trace.json|->
                        [--format human|json] [--min-confidence 0..1]
```

| Rule | Contract |
| --- | --- |
| Inputs | Exactly two inputs are required: `--before` and `--after`. Each takes a file path or `-` for standard input. At most one of the two may be `-`; a second `-` is a usage error. `--before` names the A-side trace, `--after` the B-side trace. Direction is assigned by argument role only — a trace carries no A/B marker, so there is no side-detection or swapped-input check as in `compare`. |
| Existing forms | `gatefold <input.json>`, `gatefold -`, and `gatefold compare --before … --after … --diff …` are unchanged. No existing flag is removed or retyped. `compare-traces` is additive. The single-document form remains pfl-only in v0.5: it does not accept a trace. |
| Options | `--format`, `--min-confidence`, `--help`, and `--` behave exactly as in the existing forms and may appear before or after `compare-traces`. `compare-traces` is a subcommand only in the first positional position (a file literally named `compare-traces` now needs `./compare-traces` or `gatefold -- compare-traces`); in any other position the argument remains a file path. |
| Exit codes | Unchanged: 0 success, 2 usage error, 3 input error, 4 internal error. |

## Per-document validation

Each input passes through the v0.5 trace reader defined by the
[yuurei trace contract](yuurei-trace-contract.md): byte limit, BOM handling,
the `schema_version` equality token, required fields, missing/null
semantics, and resource ceilings apply per document. A document that fails
its reader is rejected with the reader's error before any cross-trace check
runs. A document that parses as a different supported kind — for example a
pfl export passed as `--before` — is rejected with `mismatched-inputs`
naming the expected and actual document kinds.

## Cross-trace comparability

After both traces validate individually, the following checks run in this
order. Any failure is exit code 3 with the existing stable error code
`mismatched-inputs`, whose message names the mismatched fields. The
underlying rule is yuurei's: two runs are compared only when what was
requested of each cell is the same, except for the profile, whose variation
is the subject of the comparison.

| Check | Rule |
| --- | --- |
| Input-set token | When both traces carry `requested_cell`, `inputs_version` must be equal. Different input-set versions are never compared — even when the digests are equal — and are rejected. The token is compared for equality only; it is never ordered. |
| Task identity | `task.digest` must be equal. `task.source` is provenance (a path or origin), not identity: two traces may name different task paths for identical content. |
| Runtime identity | `runtime.id` must be equal. |
| Requested model | `model.requested` must be equal. |
| Isolation strategy | `isolation.strategy` must be equal. |
| Execution options | When both traces carry `execution_options`, `timeout_ms` and the `runtime` record must be equal by deep equality: object key order is not significant at any depth, array element order is. |

The following fields **may differ**; they are recorded in the result's
`inputs` metadata and surfaced as descriptive or bounded caveat claims,
never as rejections:

- `profile.name` and `profile.digest` — the harness/profile variant is the
  intended subject of the comparison. Because the profile's content is a
  digest input, two comparable runs will normally have different
  `requested_cell.digest` values.
- `requested_cell.digest` — never an acceptance criterion in either
  direction: comparability is decided by `inputs_version` and the field
  checks above, never by the digest value. A digest difference explained by
  the allowed fields is reported as a descriptive claim.
- Observed run properties — `yuurei_version`, `runtime.version`,
  `model.resolved` and `model.resolved_reason`, `isolation.verified` —
  differences here are drift between what was requested and what ran; they
  are surfaced as comparability caveats so readers do not attribute an
  outcome difference to the profile when the observed environment differed.
- Run provenance — `run_id`, `started_at`, `finished_at`, `definition`
  (`run`, `cli_overrides`) — recorded for context only.

Missing and null handling follows the trace contract: an absent optional
field is unknown, never equal or different. When `requested_cell` is absent
on either side, the `inputs_version` check is skipped and comparability
rests on the concrete field checks; a caveat claim records that the
input-set token could not be verified. The same applies to
`execution_options` absent on one side. When `requested_cell` is absent on
one side and present on the other, the comparison is not rejected — absence
is not evidence of difference. When a compared field is `null` (for example
`execution_options.timeout_ms: null` on both sides), the equal values are
still a match; a present value versus `null` is a mismatch only where the
field is required to match.

## Result contract: schema v4

The v3 comparison schema is closed (`additionalProperties: false`), its
`inputs` roles are `before`/`after`/`diff`, and its evidence `source` enum
is `["before", "after", "diff"]`. Trace comparison evidence names different
documents, so per the versioning rule v0.5 adds
[`schema/claim-result.v4.json`](../schema/claim-result.v4.json); v1, v2, and
v3 schemas and results remain valid and unchanged, the single-document
commands keep emitting v2 results, and `compare` keeps emitting v3 results.

A v4 trace-comparison result has this envelope:

| Field | Type | Meaning |
| --- | --- | --- |
| `schemaVersion` | integer `4` | Result schema version. |
| `source` | `{ command: "compare-traces" }` | Discriminator identifying this as a two-trace comparison. No single `yuurei_version` is recorded here because the inputs may carry different versions; each is recorded under `inputs`. |
| `inputs` | object | Per-trace descriptors (below). |
| `claims` | array | Comparison claims in deterministic order. |

`inputs` binds each role to the validated trace:

```text
inputs.beforeTrace / inputs.afterTrace:
  { label, document: "yuurei-trace", schemaVersion,
    runId, yuureiVersion?, startedAt, finishedAt,
    runtimeId, runtimeVersion,
    modelRequested, modelResolved, modelResolvedReason?,
    profileName, profileDigest, taskSource, taskDigest,
    isolationStrategy, isolationVerified,
    requestedCellDigest?, requestedCellInputsVersion?,
    executionOptions?, definition? }
```

`label` is the path argument exactly as supplied, or `<stdin>` when that
input was read from standard input. Labels are sanitized wherever they are
displayed; in JSON they remain the raw argument strings. `runtimeVersion`
and `modelResolved` preserve `null`. Fields absent from a trace
(`yuureiVersion`, `modelResolvedReason`, `requestedCellDigest`,
`requestedCellInputsVersion`, `executionOptions`, `definition`) are absent
from the descriptor — never rendered as null or invented. `executionOptions`
and `definition`, when present, record the trace's `execution_options` and
`definition` values verbatim so option-level and provenance drift are
auditable. The descriptor describes, never interprets.

### Claim shape

Each claim keeps the v2/v3 fields (`claim`, `ruleId`, `evidence`,
`provenance`, `confidence`) with these v4 differences:

- `evidence[]` items carry `source: "beforeTrace" | "afterTrace"` — the two
  documents a claim may cite. `pointer` is an RFC 6901 JSON Pointer into the
  trace named by `source`, per the evidence locations in the
  [yuurei trace contract](yuurei-trace-contract.md); every pointer must
  resolve to a location that exists in that trace. `elementId` is unused by
  trace claims (a trace has no element ids) and `note` keeps its meaning.
- `provenance` carries only `transform` (required, may be empty); per-trace
  metadata lives in `inputs` as on v3.
- `ruleId` is required, as on v3.

### Deterministic ordering

Claims are emitted in a fixed rule order defined by the implementation's
documented rule list, then by the compared key within a rule (usage keys,
field names) in byte order. Within a claim, evidence references are sorted
by `source` (`beforeTrace` < `afterTrace`) and then by `pointer` byte order.
Output must not depend on the order the traces were passed beyond their
assigned roles, or on filesystem iteration order.

## Claim boundaries

All v0.4 claim boundaries apply, plus these run-comparison rules:

- A claim cites only fields present in the named traces. An absent optional
  field is stated as "not recorded", a null field as "not observed" — never
  as a positive or negative value, and never as a zero.
- Claims describe recorded outcomes only. `execution.exit_code: 0` means the
  runtime process exited zero; it does not mean the task was done well, and
  no claim states or implies answer quality. `timed_out`, `signal`, and
  failure exit codes are described as execution outcomes, not verdicts.
- `usage` keys are compared only when present with a numeric value on both
  sides. A key on one side only — whether absent ("never attempted") or null
  ("attempted but unobserved") — is reported as asymmetric observation, with
  the two cases kept distinct. No delta is computed against a missing side.
- `cost` is an estimate and is phrased as one. It is compared only when both
  sides carry an estimate in the same `currency`; a null side means no
  estimate was produced, and a currency mismatch is reported as two separate
  estimates with no numeric delta.
- `duration_ms` differences are reported as recorded durations; when a side
  is null the difference is not computed.
- A trace has no pfl snapshot link: no claim associates a run with a pfl
  document, element, or snapshot — not even by matching names, paths, or
  digests.
- A difference between runs is descriptive evidence, not causation: no claim
  asserts that the profile or harness variant caused an outcome, usage, or
  cost difference.
- Claim `confidence` remains Gatefold's estimate of evidence support for the
  exact statement — independent of the run's exit status, of whether a value
  was observed, and of the comparability caveats.

## Limits

Per-document ceilings are unchanged from the trace contract and apply to
each of the two inputs independently. The aggregate input is bounded by
construction at 2 × 16 MiB. Output ceilings are unchanged: at most 50,000
emitted claims and 100,000 total evidence references; a pair whose claims
would exceed these is rejected with `invalid-shape` before output rather
than truncated.

## Errors

v0.4 error codes are unchanged and shared: a wrong document kind for a role
is `mismatched-inputs` naming the expected and actual kinds; a
comparability failure is `mismatched-inputs` naming the mismatched fields;
usage errors (missing flags, two stdin inputs, unknown options) remain exit
code 2; reader failures keep their own codes (`unsupported-version`,
`invalid-shape`, and friends).

## Representative evidence

Given two comparable traces where the run took longer on B, supported claims
could say:

> Run A resolved to model `m1` and exited 0 in 12,400 ms; run B resolved to
> model `m1` and exited 0 in 41,800 ms.

with evidence such as:

- `{ source: "beforeTrace", pointer: "/model/resolved" }`
- `{ source: "afterTrace", pointer: "/model/resolved" }`
- `{ source: "beforeTrace", pointer: "/execution/exit_code" }`
- `{ source: "afterTrace", pointer: "/execution/exit_code" }`
- `{ source: "beforeTrace", pointer: "/execution/duration_ms" }`
- `{ source: "afterTrace", pointer: "/execution/duration_ms" }`

For a comparability caveat on differing runtime versions:

- `{ source: "beforeTrace", pointer: "/runtime/version" }`
- `{ source: "afterTrace", pointer: "/runtime/version" }`

For a usage key present only on A (`output_tokens`):

- `{ source: "beforeTrace", pointer: "/usage/output_tokens" }`
- `{ source: "afterTrace", pointer: "/usage",
    note: "no output_tokens entry" }`

## Contract examples (coverage requirements)

| Case | Expected behavior |
| --- | --- |
| Comparable runs, different profiles (`profile.name`/`digest` and `requested_cell.digest` differ; identity fields match) | Accepted; claims cite `beforeTrace` and `afterTrace` evidence with valid pointers; the profile difference is described, not rejected. |
| Task digest mismatch | Rejected with `mismatched-inputs` naming `task.digest`. |
| Runtime id or requested model mismatch | Rejected with `mismatched-inputs` naming the field. |
| Isolation strategy or execution-options mismatch | Rejected with `mismatched-inputs` naming the field. |
| `requested_cell.inputs_version` differs — including when digests are equal | Rejected; digests never decide comparability. |
| Equal digests with a mismatched required field | Rejected; digest equality is not sufficient. |
| Older trace missing optional fields (`requested_cell`, `execution_options`, `definition`, `yuurei_version`, `model.resolved_reason`) | Accepted; each absent field is unknown — caveats record the unverifiable comparability inputs, never a positive or negative assertion. |
| `model.resolved: null` (with `resolved_reason` `unobserved` or `parse_failed`, or absent on an older trace) | Accepted; reported as unobserved with the reason when recorded. A resolved-model difference between two non-null values is a comparability caveat. |
| `execution` nulls (`exit_code`, `signal`, `duration_ms`), `timed_out: true`, non-zero exit | Accepted; described as recorded outcomes — unobserved stays unobserved, exit 0 is not called success of the task. |
| `usage` key absent vs null vs numeric, on either side | Only shared numeric keys are compared; asymmetric keys are reported distinctly as never-attempted or unobserved. |
| `cost` null on one side, or currency mismatch | No numeric delta; each side's estimate is stated separately when present. |
| A pfl document passed as a `compare-traces` input | Rejected with `mismatched-inputs` naming the expected and actual kinds. |
| Two `-` stdin inputs, missing flags, unknown options | Exit code 2 usage error. |

## Explicit exclusions

v0.5 does not add answer-quality judgement, score calculation, causation or
root-cause inference between harness configuration and outcomes, pfl ↔
yuurei correlation (a trace carries no snapshot link and none is inferred),
log/workspace/artifact reading, or parsing of free-text `diagnostics` into
codes. It describes what two matching yuurei traces jointly state.

## Release gate

v0.5 is releasable only when:

- `pnpm ci:all` passes from a clean install;
- real-process tests cover `compare-traces` in JSON and human output,
  including mismatched, older-trace, oversized, malformed, and stdin inputs;
- every committed trace fixture covers its contract-example row and every
  emitted claim's evidence pointers resolve inside the named input trace;
- schema v4 is validated against a committed example and the packed tarball
  ships `claim-result.v4.json` and the v4 example;
- v0.4 single-document and `compare` behavior is unchanged;
- `npm publish --dry-run` and the installed-tarball smoke test (including
  `gatefold compare-traces`) pass;
- package and documentation versions identify v0.5.
