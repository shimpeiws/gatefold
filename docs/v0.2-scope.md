# Gatefold v0.2 scope and acceptance criteria

This document locks the v0.2 boundary — report interpretation. It builds on
the [v0.1 scope](v0.1-scope.md), which stays in force: v0.2 widens what the
CLI reads and what the claims explain, without changing the claim model.

## Supported input

v0.2 accepts exactly one kind of document: a successful `pfl report --json`
export under the existing v1.x input contract
([pfl export contract](pfl-export-contract.md)).

The document reaches Gatefold through two transports:

- a file path passed as a positional argument (v0.1 behavior);
- standard input, selected by a lone `-` argument (`pfl report --json |
  gatefold -`). Stdin is an additional transport for the same document, not a
  new document kind — the same size limit, JSON validation, and contract
  checks apply.

## Output guarantees

v0.2 keeps every v0.1 guarantee and adds two:

- Every claim carries a stable `ruleId` identifying the rule that produced it,
  so JSON consumers can select claims without parsing claim text or
  `provenance.transform`. `ruleId` is an optional field in
  `schema/claim-result.v1.json`; `schemaVersion` stays `1`.
- Claims may combine input fields to explain how to read the report, and must
  cite a JSON Pointer for every input field they use.

Evidence, provenance, and confidence remain distinct from any harness quality
score. Confidence still measures how strongly the cited evidence supports the
claim — never how good the harness or the observation is.

## Observation-certainty claims

v0.2 explains the certainty of the observation the export reports. An
observation-certainty claim describes metadata the export itself carries —
`completeness`, `diagnostics`, and `data.interpretation` — and it must cite
every source field it uses.

What such a claim may say, per completeness value:

- `complete` — the export reports complete observation. The claim may state
  that fact, the count and severities of diagnostics, and the interpretation
  origin. It must not imply the harness performed well.
- `partial` — the export reports partial observation. The claim may state that
  fact, report each warning/error diagnostic the export carries (its code,
  message, and path), and state the interpretation origin. It may repeat what a
  diagnostic says; it must not extend it — e.g. it may not claim specific
  elements were missed unless a diagnostic says so.
- `unknown` — the export reports it could not determine completeness. The
  claim may state that fact and the diagnostics and interpretation origin the
  export carries. It must not speculate about coverage.

For all three: a missing optional field is absent data, not evidence of a
failure, and the claim must not infer a cause the document does not state.

## Excluded features

v0.2 does not include:

- **Other pfl commands** — `inspect`, `list`, `show`, `graph`, `snapshots`,
  `diff`, `gc`, and failure documents remain rejected.
- **Declared intent** — claims about what a harness is meant to do.
- **`yuurei` trace input** — observed execution traces are a later input
  boundary.
- **Scoring and quality ranking** — no aggregate score, no ordering of
  harnesses or rules by quality.
- **Optimization advice** — claims describe, they do not prescribe.

## Compatibility policy

- Gatefold accepts `pfl` export documents within the version range declared in
  the pfl export contract; exports outside that range fail with a non-zero exit
  and an actionable error.
- Readers ignore unknown fields, matching the `pfl` document contract.
- The Claim JSON Schema is versioned; additive changes (such as `ruleId` and
  the new optional provenance fields) keep `schemaVersion: 1`, structural
  changes bump it.
- Output stays bounded relative to input: the reader rejects reports whose
  total cited element ids exceed the documented aggregate limit.

## Release gate

v0.2 ships only when all of the following pass in a clean `pnpm install`:

- `pnpm typecheck`
- `pnpm lint`
- `pnpm format:check`
- `pnpm test --run`
- `pnpm build`
- `npm publish --dry-run` succeeds without publishing
- a smoke test of the packed CLI (`npm pack`, install the tarball, run
  `gatefold --help` and a JSON analysis from the installed binary)

The first five checks run together as `pnpm ci:all`, which must stay in sync
with this list. The publish dry-run and smoke test are exercised by the
[release checklist](release-checklist.md), not on every CI run.

## Out-of-scope record

Work recorded here is deferred to a later milestone, not dropped:

- `yuurei` observed-trace input;
- harness scoring, quality ranking, and optimization advice;
- input documents other than `pfl report --json`;
- subcommands beyond the single-input command shape.
