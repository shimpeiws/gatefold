# Gatefold v0.4 scope and comparison contract

**Status: contract definition (v0.4, issue #32).** The v0.4 CLI adds a
`compare` subcommand that explains an A → B change by joining three matching
pfl documents: A's `pfl export --json`, B's `pfl export --json`, and the
A → B `pfl diff --json`. This document defines the input, compatibility,
evidence, and result contract. It is grounded in the frozen pfl v1.0 document
contract already used by the v0.3 readers
([pfl export contract](pfl-export-contract.md),
[v0.3 scope](v0.3-scope.md)). Gatefold still does not execute pfl, inspect a
harness, read a path named inside a document, or depend on pfl at runtime.

## CLI surface

v0.4 introduces one positional subcommand:

```text
gatefold compare --before <A.json|-> --after <B.json|-> --diff <D.json|->
                 [--format human|json] [--min-confidence 0..1]
```

| Rule | Contract |
| --- | --- |
| Inputs | Exactly three inputs are required: `--before`, `--after`, `--diff`. Each takes a file path or `-` for standard input. At most one of the three may be `-`; a second `-` is a usage error. `--before` names the A-side export, `--after` the B-side export, `--diff` the A → B diff. |
| Existing forms | `gatefold <input.json>` and `gatefold -` are unchanged. No existing flag is removed or retyped. `compare` is additive. |
| Options | `--format`, `--min-confidence`, `--help`, and `--` behave exactly as in the single-document form and may appear before or after `compare`. `compare` is a subcommand only in the first positional position: `gatefold compare ...` selects the subcommand (a v0.3 invocation reading a file literally named `compare` now needs `./compare` or `gatefold -- compare`); in any other position the argument remains a file path. |
| Exit codes | Unchanged: 0 success, 2 usage error, 3 input error, 4 internal error. |

## Per-document validation

Each input passes through the existing v0.3 reader unchanged: byte limit,
BOM handling, envelope checks, command dispatch, payload shape, join
invariants, and resource ceilings apply per document. `--before` and `--after`
must parse as `command: "export"` documents and `--diff` as
`command: "diff"`; any other `command` is rejected with an error naming the
role and the actual command. A document that fails its own reader is rejected
with that reader's existing error before any cross-document check runs.

## Cross-document compatibility

After all three documents validate individually, the following checks run in
this order. Any failure is exit code 3 with a new stable error code
`mismatched-inputs` whose message names the mismatched fields and, where
applicable, the fix (for example, swapping `--before` and `--after`).

| Check | Rule |
| --- | --- |
| Project identity | `before.data.project.id` must equal `after.data.project.id`. `displayName` is descriptive only and is not part of identity. |
| Runtime identity | `before.data.runtime.id` must equal `after.data.runtime.id` and must equal `diff.data.runtime`. |
| Side detection | Before judging snapshot binding, determine which diff side each export matches: an export matches side A when `snapshot.observedSnapshotId === diff.data.observedSnapshotIdA` **and** `snapshot.resolvedSnapshotId === diff.data.resolvedSnapshotIdA`, and side B symmetrically. |
| Reversed sides | If `--before` matches side B and `--after` matches side A, the input is rejected with a diagnostic that suggests swapping the two exports. This check runs ahead of the binding verdict so the swap hint is reachable. |
| Snapshot binding | Otherwise, `--before` must match side A and `--after` side B on both observed and resolved ids. Any other combination — an export matching neither side, or both exports matching the same side — is rejected. |
| Schema/version range | Each document's `pflVersion` must already satisfy `>=1.0.0 <2.0.0` via its own reader; `snapshot.schemaVersion` and unknown additive fields follow the per-document rules. |

Version differences **within** the accepted range are not identity
contradictions. The following differences are recorded in the result's
`inputs` metadata and surfaced as bounded caveat claims, not rejections —
a comparison over a partial or version-drifted triple is still descriptive:

- `before.pflVersion` / `after.pflVersion` / `diff.pflVersion` differing;
- `before.data.resolution.semanticsVersion` differing from `after.data.resolution.semanticsVersion`;
- `before.data.interpretation.classifier.version` differing from
  `diff.data.interpretation.a.classifierVersion`, or `after` from `b`;
- `before.data.runtime.version` differing from `after.data.runtime.version`;
- `diff.data.versionNotes` entries, which are free text and are surfaced
  verbatim (sanitized), never parsed into stable codes.

Only fields the documents actually carry are compared. When a compared field
is absent or `null` (for example `runtime.version: null`), no compatibility
conclusion is drawn from that field and no caveat is invented about it.

## Result contract: schema v3

The v0.2 result schema (v2) is closed (`additionalProperties: false`), and
comparison evidence requires a new required `source` field on every evidence
reference. Per the versioning rule, v0.4 adds
[`schema/claim-result.v3.json`](../schema/claim-result.v3.json); v1 and v2
schemas and results remain valid and unchanged, and the single-document
commands keep emitting v2 results.

A v3 comparison result has this envelope:

| Field | Type | Meaning |
| --- | --- | --- |
| `schemaVersion` | integer `3` | Result schema version. |
| `source` | `{ command: "compare" }` | Discriminator identifying this as a comparison result. `pflVersion` is intentionally absent: the three inputs may carry different versions, and each is recorded under `inputs`. |
| `inputs` | object | Per-document descriptors (below). |
| `claims` | array | Comparison claims in deterministic order. |

`inputs` binds each role to the validated document:

```text
inputs.before / inputs.after:
  { label, command: "export", pflVersion,
    observedSnapshotId, resolvedSnapshotId,
    completeness, runtimeVersion, semanticsVersion,
    classifierVersion, interpretationOrigin }
inputs.diff:
  { label, command: "diff", pflVersion,
    observedSnapshotIdA, observedSnapshotIdB,
    resolvedSnapshotIdA, resolvedSnapshotIdB,
    completeness, classifierVersionA, classifierVersionB,
    interpretationOriginA, interpretationOriginB }
```

`label` is the path argument exactly as supplied, or `<stdin>` when that
input was read from standard input. Labels are sanitized wherever they are
displayed; in JSON they remain the raw argument strings. `runtimeVersion`
preserves `null`. The version, semantics, classifier, and completeness
fields are what make the differences listed above auditable in the result;
they describe, never interpret.

### Claim shape

Each claim keeps the v2 fields (`claim`, `ruleId`, `evidence`, `confidence`)
with these v3 changes:

- `evidence[]` items gain a required `source` field:
  `{ source: "before" | "after" | "diff", pointer, elementId?, note? }`.
  `pointer` is an RFC 6901 JSON Pointer into the document named by `source`,
  and every pointer must resolve to a location that exists in that document.
  `elementId` and `note` keep their v2 meaning.
- `provenance` carries only `transform` (required, may be empty). The v2
  provenance fields that name a single document move to `inputs` under these
  names: `sourceFile` → `label`, `exportVersion` → `pflVersion`,
  `observedSnapshotId`/`resolvedSnapshotId` keep their names on each export
  descriptor (the diff descriptor carries both A and B ids),
  `classifierVersion` → `classifierVersion` (export) /
  `classifierVersionA`/`classifierVersionB` (diff), and
  `interpretationOrigin` → `interpretationOrigin` (export) /
  `interpretationOriginA`/`interpretationOriginB` (diff). `runtimeName` —
  which only report documents carry — has no `inputs` counterpart; exports
  carry `runtime.id`/`runtime.version`, and `runtime.version` is recorded as
  `runtimeVersion`.
- `ruleId` is required in v3 (all v3 documents are produced by this release
  or later).

### Deterministic ordering

Claims are emitted in a fixed rule order defined by the implementation's
documented rule list, then by element id (lexicographic), then by claim
identity within a rule. Within a claim, evidence references are sorted by
`source` (`before` < `after` < `diff`) and then by `pointer` byte order.
Output must not depend on the order the documents were passed beyond their
assigned roles, or on filesystem iteration order.

## Claim boundaries

All v0.3 claim boundaries apply, plus these comparison-specific rules:

- A claim cites only fields present in the named documents. Absent or `null`
  layers are stated as "no entry", never as a negative property.
- `structural.addedIds`/`removedIds`/`changedIds` and `statusChanges` may be
  joined to the exports by element id; claims distinguish observed structural
  change, resolved-status change, and interpretation change.
- `effective.newlyEffective`/`noLongerEffective`, `activationChanged`, and
  `facetDeltas` are aggregate values. They may be reported as aggregates but
  must never be attributed to a specific element; a positive facet delta is
  not evidence that a given element gained that facet.
- `effective` remains static potential, not runtime use; no claim asserts an
  element was loaded, executed, or beneficial.
- A relation's appearance is descriptive evidence, not proof of a root cause.
- A finding's identity is `(rule, message, elementIds)`; a reworded message
  appears as a removal plus an addition and is reported as such, without
  asserting a semantic resolution from wording alone.
- Partial observation (`completeness: "partial"`, opaque inspectability,
  unknown statuses, absent layers) limits what claims may say: uncertainty is
  preserved, never upgraded.
- Claim `confidence` remains Gatefold's estimate of evidence support for the
  exact statement — independent of pfl resolution confidence, per-element
  classification confidence, and envelope completeness.

## Limits

Per-document ceilings are unchanged from v0.3 and apply to each of the three
inputs independently. The aggregate input is bounded by construction at
3 × 16 MiB. Output ceilings are unchanged: at most 50,000 emitted claims and
100,000 total evidence references; a triple whose claims would exceed these
is rejected with `invalid-shape` before output rather than truncated.

## Errors

v0.3 error codes are unchanged. v0.4 adds one code:

| Code | Meaning |
| --- | --- |
| `mismatched-inputs` | The three documents parsed but fail a cross-document compatibility check (wrong command for a role, project or runtime mismatch, snapshot ids that do not bind to the diff's A/B sides, reversed exports). |

Wrong-document-kind-for-a-role is reported as `mismatched-inputs` naming the
expected and actual `command`. Usage errors (missing flags, two stdin
inputs, unknown options) remain exit code 2.

## Representative evidence

Given an element `el_a` present only in the after export and listed in the
diff's `addedIds`, a supported claim could say:

> Element `el_a` was added between A and B; pfl observed it as a project
> instruction and resolved it as effective.

with evidence such as:

- `{ source: "diff", pointer: "/data/structural/addedIds/0", elementId: "el_a" }`
- `{ source: "after", pointer: "/data/elements/2/id", elementId: "el_a" }`
- `{ source: "after", pointer: "/data/elements/2/observed/native/kind" }`
- `{ source: "after", pointer: "/data/elements/2/resolved/status" }`

For a status change on an element present in both exports:

- `{ source: "diff", pointer: "/data/effective/statusChanges/0" }` plus the
  element's `resolved/status` pointer in each export.

## Contract examples (coverage requirements)

| Case | Expected behavior |
| --- | --- |
| Matching triple | Accepted; claims cite `before`, `after`, and `diff` evidence with valid pointers. |
| Swapped A/B | `--before` binding to the diff's B side is rejected with `mismatched-inputs` suggesting the swap. |
| Unrelated project or runtime | Rejected with `mismatched-inputs` naming the field. |
| Mixed pfl 1.x versions / differing `semanticsVersion` or classifier versions | Accepted; differences recorded in `inputs` and surfaced as caveat claims. |
| Partial observation (`completeness: "partial"`, opaque elements) | Accepted; claims preserve the observation limits. |
| Absent layers (`resolved`/`interpretation` `null`) | Accepted; claims state the absence without inventing properties. |
| Wrong command for a role (e.g. a report passed as `--before`) | Rejected with `mismatched-inputs`. |
| Two `-` stdin inputs, missing flags, unknown options | Exit code 2 usage error. |

## Explicit exclusions

v0.4 does not add performance inference, quality ranking, root-cause
inference, prescriptions, runtime-trace correlation (yuurei), bundle-manifest
verification, or parsing of free-text `versionNotes`. It describes what three
matching pfl documents jointly state.
