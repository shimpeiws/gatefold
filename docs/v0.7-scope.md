# Gatefold v0.7 scope and Outcome-evaluation contract

**Status: implemented (v0.7; issues #59–#64 under milestone #58).
Deprecated at v0.11 — see [Ownership and deprecation](#ownership-and-deprecation).**
v0.7 is Gatefold's first bounded **Outcome** judgement: it evaluates one
seeded yuurei run against an explicit task-evaluation specification, and it
compares two evaluated runs criterion by criterion. Evidence comes only from
verified run artifacts and independently produced check reports — never from
the agent's prose, logs, or unverified bytes. This document defines the task
spec, criteria, verdicts, check reports, comparability, and result contract.
It builds on the [run-directory contract](yuurei-run-contract.md), the
[seeded-run additions](yuurei-seeded-run-contract.md), and the v0.5
comparability rules ([v0.5 scope](v0.5-scope.md)).

## CLI surface

v0.7 adds two positional subcommands:

```text
gatefold evaluate-run --run <run-dir> --spec <task-spec.json>
                      [--check-report <report.json>] ...
                      [--format human|json] [--min-confidence 0..1]

gatefold compare-evaluations --before <A-run-dir> --after <B-run-dir>
                      --spec <task-spec.json>
                      [--before-check-report <report.json>] ...
                      [--after-check-report <report.json>] ...
                      [--format human|json] [--min-confidence 0..1]
```

| Rule | Contract |
| --- | --- |
| `evaluate-run` inputs | `--run` names one yuurei run directory; `--spec` names the task-evaluation spec JSON file. `--check-report` is optional and repeatable; each occurrence names one external check-report JSON file bound to that run. Directories cannot arrive on stdin: `-` is rejected as a flag value with a usage error. |
| `compare-evaluations` inputs | `--before`/`--after` name the A/B run directories, `--spec` names the shared task spec. `--before-check-report` and `--after-check-report` are optional and repeatable, one report per occurrence, bound to the matching side only. `-` is rejected everywhere. |
| Existing forms | `gatefold <input.json>`, `gatefold -`, `gatefold compare …`, `gatefold compare-traces …`, and `gatefold compare-runs …` are unchanged. The new names are subcommands only in the first positional position. |
| Options / exit codes | `--format`, `--min-confidence`, `--help`, and `--` behave exactly as in the existing forms. Exit codes unchanged: 0 success, 2 usage error, 3 input error, 4 internal error. |

## Task-evaluation spec

The spec is a versioned JSON document the caller supplies:

```json
{
  "specVersion": 1,
  "rubricId": "auth-repair-v1",
  "task": { "digest": "sha256:…" },
  "baseline": { "digest": "sha256:…" },
  "criteria": [
    { "id": "fix-applied", "kind": "file-modified", "path": "src/auth.ts" },
    { "id": "tests-added", "kind": "file-added", "path": "test/auth.test.ts" },
    { "id": "answer-mentions-fix", "kind": "final-result-contains",
      "text": "token expiry" },
    { "id": "answer-json", "kind": "final-result-json-field",
      "pointer": "/status", "equals": "fixed" },
    { "id": "unit-tests", "kind": "external-check" }
  ]
}
```

| Field | Type | Meaning |
| --- | --- | --- |
| `specVersion` | integer `1`, required | Spec format version; any other value is `unsupported-version`. |
| `rubricId` | string, required, non-empty | Stable rubric identifier. Two evaluations are rubric-comparable only under equal `rubricId` and `specVersion`. |
| `task.digest` | string, required | The task content digest the run must record (`trace.task.digest`). |
| `baseline` | object, optional | `{ digest }`: the seeded baseline identity the run must record (`seed.baseline.requested_digest`). Omit for specs that accept legacy empty-workspace runs. |
| `criteria` | array, required, non-empty | The declarative criteria to evaluate, in spec order. Each entry has a unique `id` (non-empty string) and a `kind`. |

A spec that is not an object, lacks a required field, carries an unsupported
criterion `kind`, repeats a criterion `id`, or violates a scalar ceiling is
rejected (`invalid-shape` / `unsupported-version`, exit 3). Unknown top-level
and per-criterion fields are ignored, matching yuurei's additive-change rule.

### Supported criterion kinds

| `kind` | Parameters | `pass` means | `fail` means |
| --- | --- | --- | --- |
| `file-added` | `path` | The verified patch records `path` as an `added` file. | The patch is complete and records `path` as `modified`/`deleted`, or does not record it while recording other files past it. |
| `file-modified` | `path` | The verified patch records `path` as `modified`. | The patch is complete and records `path` as `added`/`deleted`, or a complete patch does not record it. |
| `file-deleted` | `path` | The verified patch records `path` as `deleted`. | The patch is complete and records `path` as `added`/`modified`, or a complete patch does not record it. |
| `final-result-exact` | `text` | The verified `result.txt`, normalized per the rules below, equals `text`. | Verified normalized text differs from `text`. |
| `final-result-contains` | `text` | The verified `result.txt` contains `text` after normalization. | Verified normalized text does not contain `text`. |
| `final-result-json-field` | `pointer`, `equals` | The verified `result.txt` parses as JSON and the RFC 6901 `pointer` resolves to a value equal to `equals`. | The text parses but the pointer is absent or resolves to a different value. |
| `external-check` | — | An accepted check report records a `pass` verdict for this criterion id. | An accepted check report records a `fail` verdict for this criterion id. |

Text normalization for `final-result-*` criteria is deterministic: the stored
bytes are decoded as UTF-8 (a decode failure is uninterpretable), a single
leading U+FEFF is stripped, and CRLF line endings are normalized to LF. No
whitespace collapsing, case folding, or other fuzzy matching is applied —
`exact` means exact after that normalization.

## Verdicts

Every criterion resolves to exactly one verdict:

| Verdict | Meaning |
| --- | --- |
| `pass` | The cited verified evidence establishes the criterion. Never emitted from unverified, partial, or inferred evidence. |
| `fail` | The cited verified evidence establishes the criterion is not satisfied. |
| `unknown` | The evidence cannot establish either outcome: the needed artifact is absent, unverified, truncated across the cited region, malformed, contradictory, or the criterion cannot be evaluated for this run kind. |

Each evaluation records `verdict`, a human-readable `reason`, `evidence`
references, `provenance`, and `confidence`. **Confidence is separate from the
verdict**: it is Gatefold's estimate of evidential support, not of outcome
quality. A `pass` at 1.0 confidence is still only "the named criterion was
satisfied by the cited evidence" — never a correctness or quality judgement.

### Unknown-producing conditions

| Condition | Effect |
| --- | --- |
| `patch.diff` absent, `missing`, `unverified`, `digest-mismatch`, or `malformed` | All `file-*` criteria are `unknown`; the patch entry state is cited. |
| `patch.state` `"absent"`, or the generation-failed diagnostic | All `file-*` criteria are `unknown`: no change record exists to judge against. |
| `patch.state` `"partial"`, patch `verified-truncated`, or a counted omission diagnostic on a trace without the `patch` record | `file-*` criteria resolvable from the recorded changes evaluate normally; a criterion whose file is absent is `unknown` — the file may be an omitted change — citing `/patch/state`, the entry, or the diagnostic. |
| `patch.state` `"complete"` over verified untruncated bytes | The patch is authoritative: an absent criterion file is `fail`. |
| `result.txt` absent / `not-emitted` / `parse-failed` / `save-failed` / `not-recorded` | All `final-result-*` criteria are `unknown` with the corresponding reason. |
| `result.txt` `digest-mismatch` / `unverified` / `verified-truncated` | `final-result-*` criteria are `unknown` (a truncated result cannot establish `exact`/`contains`/`json-field`). |
| `file-modified` / `file-deleted` on a legacy empty-workspace run | `unknown`: an all-additions patch cannot express modification or deletion against a baseline. |
| `final-result-json-field` when the verified `result.txt` is not a JSON document | `fail`: the criterion required a JSON field and the verified evidence affirmatively shows none exists. The same holds when the text parses as JSON but the pointer is absent or resolves to a different value. Only absent/unverified/truncated evidence is `unknown`. |
| `external-check` with no accepted report, a rejected report, a missing result row, or conflicting rows | `unknown` with the binding-specific reason. |

## External check reports

A check report is a versioned JSON document produced by an external evaluator
or test runner — Gatefold never executes tests and never accepts the agent's
own stdout/stderr or final-answer claims as a check result:

```json
{
  "reportVersion": 1,
  "evaluator": { "id": "jest", "version": "29.7.0" },
  "subject": {
    "taskDigest": "sha256:…",
    "baselineDigest": "sha256:…",
    "patchDigest": "sha256:…"
  },
  "results": [
    { "criterionId": "unit-tests", "verdict": "pass",
      "suite": "auth.test.ts" }
  ]
}
```

| Field | Type | Meaning |
| --- | --- | --- |
| `reportVersion` | integer `1`, required | Report format version; any other value is `unsupported-version`. |
| `evaluator.id` | string, required | Identity of the evaluator/test runner that produced the report. `evaluator.version`, `suite` (per row), and `note` (per row) are optional provenance. |
| `subject.taskDigest` | string, required | Must equal the run's `trace.task.digest`. |
| `subject.baselineDigest` | string, optional | When present, must equal the run's `seed.baseline.requested_digest`. |
| `subject.patchDigest` | string, optional | When present, must equal the run's verified `patch.diff` manifest digest. |
| `results` | array, required, may be empty | Rows of `{ criterionId, verdict }` with `verdict ∈ pass\|fail\|unknown`. |

**Binding and acceptance.** A report is accepted only when it parses, its
declared subject matches the bound run, and every row is well-formed. The
outcomes below describe rejection — a rejected report can never imply a pass;
each `external-check` criterion it could have answered becomes `unknown` with
the rejection reason, and the report is described in `inputs` with its error:

- malformed JSON / bad shape → `invalid` report;
- subject `taskDigest`/`baselineDigest`/`patchDigest` mismatch → `mismatched`
  report;
- a row naming a criterion id not declared `external-check` in the spec → that
  row is ignored (other rows still apply);
- duplicate `criterionId` rows with **identical** verdicts collapse to one;
  duplicate rows with **conflicting** verdicts leave the criterion `unknown`
  with a conflict reason;
- a `pass`/`fail` row supplies the criterion verdict; an `unknown` row yields
  `unknown`; a criterion with no row is `unknown` (missing result).

Every accepted verdict carries the evaluator's identity and a `checkReport`
evidence pointer to its row.

## A/B comparability for evaluations

Two runs are evaluation-comparable only when **all** of these hold; any
failure is `mismatched-inputs` (exit 3), naming the mismatched fields:

- both runs' `trace.task.digest` equal the spec's `task.digest`;
- both runs record the spec's `baseline.digest` when the spec declares one —
  a spec without `baseline` accepts either run kind, but a seeded A run and a
  legacy B run are never comparable;
- the v0.5 run-condition checks hold between the two traces
  (`requested_cell.inputs_version`, `runtime.id`, `model.requested`,
  `isolation.strategy`, and `execution_options` when both record it), with the
  same caveat claims for allowed differences — **profile difference is
  allowed** and remains the compared variable;
- the single supplied spec fixes the rubric (`rubricId`, `specVersion`,
  criterion set) for both sides, so rubric comparability holds by
  construction.

Before comparability runs, each side's spec binding is checked: the spec's
`task.digest` must equal the run's `trace.task.digest`, and a declared
`baseline.digest` must equal the run's `seed.baseline.requested_digest` — a
seeded run whose baseline differs is rejected rather than evaluated against
the wrong seed. **No criterion is ever evaluated against the wrong
baseline.**

## Result contracts: schemas v6 and v7

`evaluate-run` emits [`schema/claim-result.v6.json`](../schema/claim-result.v6.json);
`compare-evaluations` emits
[`schema/claim-result.v7.json`](../schema/claim-result.v7.json). Schemas v1–v5
and their commands are unchanged.

### v6 envelope

| Field | Type | Meaning |
| --- | --- | --- |
| `schemaVersion` | integer `6` | Result schema version. |
| `source` | `{ command: "evaluate-run" }` | Discriminator. |
| `inputs` | object | `{ run, spec, checkReports }` descriptors (below). |
| `context` | object | Observed run context preserved separately from verdicts: `execution` (`exitCode`, `signal`, `timedOut`), `model` (`requested`, `resolved`, `resolvedReason`), `usage`, `cost`. Describes recorded state only. |
| `evaluations` | array | One entry per spec criterion, in spec order. |

`inputs.run` is the run descriptor of the v5 schema plus `seeded`,
`baseline` (`{ digest, materializedDigest, source, head }` or `null`),
`changes` (`{ added, modified, deleted }` or `null` — `null` when the run's
change set is unknown, never "no changes"), `patchRecord`
(`{ base, state }` or `null` on traces that predate the record), and
`patchState`/`resultState` fields. `inputs.spec` is `{ label, rubricId,
specVersion, criterionCount }`. `inputs.checkReports[]` is
`{ label, evaluatorId, state, error?, resultCount }` with `state ∈ accepted |
invalid | mismatched`.

Each `evaluations[]` entry:

```text
{ criterionId, kind, verdict: "pass"|"fail"|"unknown",
  reason: string, confidence: 0..1,
  evidence: [ EvidenceReference, ... ],   // min 1
  provenance: { transform: [...] } }
```

Evidence sources extend the v5 set: single-run forms `trace`, `manifest`,
`patch`, `result`, `spec`, and `checkReport`, plus `before*`/`after*` forms in
v7. `trace`/`manifest` pointers resolve inside the run's documents;
`patch`/`result` pointers are the artifact's manifest-entry pointer with the
verified `digest` and bounded `lines`/`bytes`; `spec` and `checkReport`
pointers resolve inside the supplied documents.

### v7 envelope

Same shape with `source.command = "compare-evaluations"`, `inputs` =
`{ beforeRun, afterRun, spec, beforeCheckReports, afterCheckReports }`,
`context` = `{ before, after }` run contexts, and a `transitions` array —
one entry per spec criterion, in spec order:

```text
{ criterionId, before: verdict, after: verdict,
  changed: boolean, reason: string, confidence: 0..1,
  evidence: [...], provenance: { transform: [...] } }
```

`before`/`after` carry each side's verdict, including `unknown`. **There is
no global score and no aggregate pass count** — transitions are reported
criterion by criterion only. The v0.5 comparability caveats (allowed
A/B differences and verification gaps) are emitted alongside in `caveats`
as `{ field, text, evidence }` records; an observed transition never
asserts which harness change caused it.

### Deterministic ordering

Evaluations follow spec criterion order; transitions likewise. Within an
entry, evidence references are sorted by source order (`trace`/`spec`/
`manifest`/`patch`/`result`/`checkReport`, `before*` before `after*`) then by
pointer byte order. Output never depends on manifest entry order, patch block
order, result-row order, or filesystem iteration.

## Claim boundaries

- Only `verified`/`verified-truncated` artifact bytes ever feed a verdict; a
  `pass` never comes from unverified, missing, or contradictory evidence.
- All agent-produced text — the patch content, `result.txt`, stdout/stderr —
  is data: parsed for comparison, never executed, never inferred into test
  success, and sanitized wherever it reaches output.
- A `pass` means only that the named criterion was satisfied by the cited
  evidence; no universal quality score, ranking, or causal claim is emitted.
- Execution status, model identity, usage/cost, artifact availability,
  verdict, and confidence are kept distinct; none implies another.
- A transition A → B states what changed per criterion; it does not assert
  which harness change caused it.

## Limits

Document ceilings are unchanged: each of `trace.json`, `artifacts.json`,
`patch.diff`, `result.txt`, the spec, and every check report honors the shared
16 MiB bound. Spec limits: at most 1,000 criteria and the shared 4,096-char
scalar ceiling. Check-report limits: at most 10,000 result rows. Output
ceilings are unchanged: at most 50,000 emitted evaluations/transitions and
100,000 total evidence references; excess is rejected with `invalid-shape`
rather than truncated.

## Errors

| Condition | Code | Exit |
| --- | --- | --- |
| Missing/duplicated flags, `-` where a directory is required | usage error | 2 |
| Unreadable run directory, spec, or report file | `unreadable-file` | 3 |
| Spec/report not valid JSON | `invalid-json` | 3 |
| Spec/report shape or version violation; `seed`/`patch` shape or consistency violation | `invalid-shape` / `unsupported-version` | 3 |
| Spec `task.digest`/`baseline.digest` vs run mismatch; A/B comparability failure | `mismatched-inputs` | 3 |

A **rejected check report** is not an input error: evaluation proceeds, the
report's state is described in `inputs`, and affected criteria become
`unknown`.

## Contract examples (coverage requirements)

| Case | Expected behavior |
| --- | --- |
| Seeded run, spec binding ok, `file-modified` recorded | `pass` citing the patch block's verified range. |
| Seeded run, `file-added` path absent from a complete patch | `fail` citing the patch entry. |
| Legacy empty-workspace run, `file-added` | Evaluates against the all-additions patch. |
| Legacy run, `file-modified`/`file-deleted` | `unknown` — no baseline-relative record exists. |
| `final-result-contains` with matching `result.txt` | `pass` citing the result bytes range. |
| `result.txt` absent and a `result:` diagnostic recorded | `unknown` citing the trace `diagnostics` pointer. |
| `patch.state` `"partial"` over a verified patch | Recorded changes evaluate normally; an absent criterion file is `unknown` citing `/patch/state`. |
| `result.txt` `digest-mismatch` | `unknown`; bytes never interpreted. |
| Patch `verified-truncated` cutting before the criterion's file | `unknown` — the file may be in the cut tail. |
| Spec `task.digest` ≠ run `task.digest` | `mismatched-inputs`, exit 3. |
| Spec `baseline.digest` ≠ seeded `baseline.digest` | `mismatched-inputs`, exit 3 — never evaluated against the wrong baseline. |
| Accepted check report `pass`/`fail` row | Verdict applied, citing the row pointer and evaluator id. |
| Check report subject digest mismatch | Report `mismatched`; affected criteria `unknown`. |
| Conflicting duplicate rows for one criterion | Criterion `unknown` with conflict reason. |
| Comparable runs, `pass → fail` / `fail → pass` / `unknown → pass` / unchanged | One transition per criterion; unchanged transitions marked `changed: false`. |
| Baseline/rubric/condition mismatch between sides | `mismatched-inputs`, exit 3. |
| Hostile text in `result.txt` or patch content | Treated as data; sanitized on display; never executed. |

## Explicit exclusions

v0.7 does not add: a universal quality score or ranking; causal attribution of
a transition to a harness change; command/code execution; an LLM judge;
free-text log parsing; `workspace/` reading; or inference from the agent's own
stdout/stderr/final answer into a test result. Gatefold does not run the agent
or the tests.

## Ownership and deprecation

**Decision (v0.11, issue #88).** Contract evaluation and verdict ownership
belong to the separate `analyze` layer; Gatefold owns evidence binding,
comparison, and audit. `evaluate-run` and `compare-evaluations` are
therefore **deprecated**: they remain functional and frozen at schema
v6/v7 — same inputs, outputs, exit codes, and admissibility rules — for
the whole Gatefold 1.x line. Removal is a 2.0 decision, to be taken only
after analyze ships the contract surface that supersedes them. Gatefold
never imports or executes analyze to keep these commands alive.

Deprecation is a contract-level signal: `--help` marks the commands, the
v6/v7 schemas carry `"deprecated": true`, and this document records the
mapping. Successful runs keep stderr empty — no runtime warning is added,
so existing pipelines and the supplied-evaluation lane are undisturbed.

### What is reusable evidence handling vs criterion evaluation

| Reusable evidence layer (stays Gatefold-owned) | Verdict layer (deprecated; migrates to analyze) |
| --- | --- |
| Run-directory reading and digest verification (`src/input/yuurei-*.ts`) | Task-spec criteria model (`src/input/task-spec.ts`) |
| Check-report document parsing and subject-digest binding (`src/input/check-report.ts`, `src/application/check-report-binding.ts`) — also used by `audit-run` | Criterion resolution to `pass`/`fail`/`unknown` (`src/application/evaluate-run.ts`, `src/application/compare-evaluations.ts`, `src/domain/evaluation.ts`) |
| Evidence citation and run-descriptor identity in v6/v7 results | The v6 `evaluations[]` / v7 `transitions[]` verdict entries |

The check-report *document contract* (`reportVersion: 1`, subject digests,
result rows) is unchanged: `audit-run --check-report` keeps auditing
declared subjects, and `report-cell`/`compare-cells` keep binding supplied
v6/v7 results — presented as **supplied legacy verdicts**, never recomputed
or restated as Gatefold-observed facts.

### Migration mapping to the analyze model

| v0.7 concept | analyze-side counterpart | Notes |
| --- | --- | --- |
| task spec (`specVersion: 1`, `rubricId`, `task`/`baseline` digests, `criteria[]`) | a Contract: proposition set plus subject binding | `rubricId`+`specVersion` comparability maps to Contract identity; criterion `kind`s name which evidence class may decide them |
| `file-added`/`file-modified`/`file-deleted` | predicate over verified patch records | eligibility: complete patch → authoritative; partial/truncated patch → unestablished absence, never fail |
| `final-result-exact`/`contains`/`json-field` | predicate over verified `result.txt` bytes | the v0.7 normalization (UTF-8, one BOM, CRLF→LF) is part of the evidence definition, not the predicate |
| `external-check` | predicate over a bound external report | binding (subject digests) is Gatefold evidence; the row verdict is the report's self-declaration |
| verdict `pass`/`fail` | analyze verdict on an admitted proposition | only ever from verified evidence |
| verdict `unknown` | **not** `inconclusive`/`observation_failed`: it means *the evidence cannot establish either outcome* — the consumer must classify from the entry's `reason`/evidence (missing vs rejected vs conflicting vs truncated) | a silent re-label loses the distinction between absent evidence and present-but-disqualified evidence |
| `confidence` | none | evidential-support estimate internal to v0.7; it is not a probability of correctness and does not migrate |
| `inputs.checkReports[].state` | admission record of a supplied report | `accepted`/`invalid`/`mismatched` map to analyze's admission decision on the supplied document |
| v7 `transitions[]` | per-criterion A → B of admitted verdicts | `changed: false` and `unknown`→`x` transitions must survive; no aggregate |

**Unsupported semantics, explicitly:** Gatefold has no `satisfied`/
`violated` vocabulary to map into; an `unknown` verdict carries no machine
sub-state (the `reason` text and `evidence` are the only decomposition);
and nothing in v6/v7 attests that an evaluator *executed* — check-report
subject digests are self-declarations (see the self-declaration caveat
above). A migration that needs any of those must get them from analyze's
own contract, not from re-reading Gatefold output.

### Compatibility policy

- v6/v7 documents remain readable forever; `schema/claim-result.v6.json`
  and `v7.json` stay published and `schemaVersion`/`source.command`
  identify them.
- `report-cell --evaluation` and `compare-cells --evaluation` keep
  accepting conforming v6/v7 documents — including ones produced before
  the deprecation — as supplied legacy verdicts.
- No new criterion kinds, verdict states, or v6/v7 fields will be added;
  the surface is frozen, not maintained.
- The `evaluate-run`/`compare-evaluations` commands, flags, and exit
  codes are unchanged until removal; scripts that keep working today keep
  working through 1.x.

## Release gate

v0.7 is releasable only when:

- `pnpm ci:all` passes from a clean install;
- real-process tests cover both commands in JSON and human output across the
  contract-example rows;
- every emitted evidence reference resolves inside the named document and
  range;
- schemas v6/v7 validate against committed examples and the packed tarball
  ships both plus the new examples;
- v0.1–v0.6 commands and schemas are unchanged;
- the installed-tarball smoke test (including `evaluate-run` and
  `compare-evaluations`) passes;
- package and documentation versions identify v0.7.
