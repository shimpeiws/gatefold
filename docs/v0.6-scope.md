# Gatefold v0.6 scope and run-directory comparison contract

**Status: implemented (v0.6; contract in #52, implementation in #53–#56).**
The v0.6 CLI adds a `compare-runs` subcommand that explains an A → B
difference between two comparable yuurei **run directories**: it validates
each run's `artifacts.json` manifest, verifies the recorded digests of the
artifacts it reads, and compares the generated files each run's `patch.diff`
records. This document defines the input, comparability, evidence, and result
contract. It is grounded in the [yuurei run-directory contract](yuurei-run-contract.md)
and reuses the v0.5 comparability rules unchanged
([v0.5 scope](v0.5-scope.md)). Gatefold still does not execute yuurei, never
reads `workspace/` or logs, and never follows a path recorded inside a run
document.

## CLI surface

v0.6 introduces one positional subcommand:

```text
gatefold compare-runs --before <A-run-dir> --after <B-run-dir>
                      [--format human|json] [--min-confidence 0..1]
```

| Rule | Contract |
| --- | --- |
| Inputs | Exactly two inputs are required: `--before` and `--after`. Each takes a path to a yuurei run directory (a directory containing `trace.json` and `artifacts.json`). `--before` names the A-side run, `--after` the B-side run. A run directory cannot arrive on standard input: `-` is rejected as a flag value with a usage error. |
| Existing forms | `gatefold <input.json>`, `gatefold -`, `gatefold compare …`, and `gatefold compare-traces …` are unchanged. `compare-runs` is additive and is a subcommand only in the first positional position (a directory literally named `compare-runs` needs `./compare-runs` or `gatefold -- compare-runs`). |
| Options | `--format`, `--min-confidence`, `--help`, and `--` behave exactly as in the existing forms and may appear before or after `compare-runs`. |
| Exit codes | Unchanged: 0 success, 2 usage error, 3 input error, 4 internal error. |

## Per-run loading

Each run directory is loaded per the
[run-directory contract](yuurei-run-contract.md): `trace.json` passes through
the v0.5 trace reader, `artifacts.json` is validated as a manifest, every
entry's path is checked for confinement, and `patch.diff` — when listed — is
read, digest-verified, and parsed. A directory that fails loading is rejected
with the reader's error before any cross-run check runs.

## Cross-run comparability

The v0.5 comparability policy applies to the two runs' traces unchanged:
same `requested_cell.inputs_version` token, `task.digest`, `runtime.id`,
`model.requested`, `isolation.strategy`, and — when both record it —
`execution_options`. Any failure is exit code 3 with `mismatched-inputs`
naming the mismatched fields; the allowed differences produce the same
caveat claims as `compare-traces`. The artifact comparison runs only after
both runs are accepted as comparable.

## Result contract: schema v5

v0.6 adds [`schema/claim-result.v5.json`](../schema/claim-result.v5.json);
v1–v4 schemas and results remain valid and unchanged, the single-document
commands keep emitting v2 results, `compare` keeps emitting v3, and
`compare-traces` keeps emitting v4.

A v5 run-comparison result has this envelope:

| Field | Type | Meaning |
| --- | --- | --- |
| `schemaVersion` | integer `5` | Result schema version. |
| `source` | `{ command: "compare-runs" }` | Discriminator identifying this as a two-run-directory comparison. |
| `inputs` | object | Per-run descriptors (below). |
| `claims` | array | Comparison claims in deterministic order. |

`inputs` binds each role to the loaded run directory:

```text
inputs.beforeRun / inputs.afterRun:
  { label, document: "yuurei-run",
    trace: { …the v4 traceInput fields… },
    patchState,
    artifacts: [ { path, kind, digest, truncated?, bytes?, state } ] }
```

`label` is the directory argument exactly as supplied; it is sanitized
wherever it is displayed. `trace` is the trace descriptor of the v4 schema
(labelled `<label>/trace.json`), verbatim. `artifacts` preserves the
manifest's facts — `path`, `kind`, `digest`, `truncated` when present, the
stored `bytes` when the file was read — plus the entry's verification
`state` (`verified`, `verified-truncated`, `digest-mismatch`, `missing`,
`unverified`). `patchState` summarizes the `patch.diff` situation for quick
consumption: the entry's state when listed, `malformed` when verified bytes
violate the patch grammar, or `not-recorded` when the manifest lists no
`patch.diff` entry. Descriptors describe, never interpret.

### Claim shape

Each claim keeps the v4 fields (`claim`, `ruleId`, `evidence`,
`provenance`, `confidence`); `provenance` carries only `transform`, and
`ruleId` is required. `evidence[]` items extend the v4 reference:

- `source` ∈ `beforeTrace | afterTrace | beforeManifest | afterManifest |
  beforePatch | afterPatch` — the run side and the document inside it.
- `pointer` is an RFC 6901 JSON Pointer into that document, per the
  [evidence locations](yuurei-run-contract.md#evidence-locations). For the
  `*Patch` sources it is the manifest pointer of the `patch.diff` entry, so
  the cited bytes stay bound to a manifest record.
- `digest` — required on `*Patch` evidence: the verified stored digest the
  range resolves against.
- `path` — on `*Patch` evidence citing a generated file, the file's
  workspace-relative path.
- `lines` `{start, end}` / `bytes` `{start, end}` — on `*Patch` evidence, a
  1-based inclusive line range / 0-based half-open byte range inside the
  stored patch bytes.
- `elementId` is unused by run claims; `note` keeps its meaning.

### Deterministic ordering

Claims are emitted in the rule order documented in
[rules.md](rules.md#compare-runs-rules), then by the compared key within a
rule — artifact path or generated-file path — in UTF-8 byte order. Within a
claim, evidence references are sorted by `source` (`beforeTrace` <
`afterTrace` < `beforeManifest` < `afterManifest` < `beforePatch` <
`afterPatch`) and then by `pointer` byte order. Output must not depend on
manifest entry order, patch block order, filesystem iteration order, or the
order the directories were passed beyond their assigned roles.

## Claim boundaries

All v0.4/v0.5 claim boundaries apply to the trace-level claims, plus these
artifact-comparison rules:

- Only `verified` and `verified-truncated` patch bytes are interpreted. A
  `digest-mismatch`, `malformed`, `missing`, `unverified`, or not-recorded
  patch contributes no file-level claims — only a caveat describing the
  state. A truncated patch's claims describe the stored prefix only and say
  so.
- A missing `patch.diff` is never "the run produced no output"; a file
  absent from a patch is never "the run did not write it" — yuurei omits
  binary, oversized, over-cap, and unrepresentably named files.
- Each patch is additions against an empty workspace, so the comparison
  describes two sets of generated outputs. It never describes edits against
  a project baseline, and a content difference is never called an
  improvement, a regression, or a sign of task success.
- Patch content and generated paths are data: they are parsed, never
  executed, and sanitized wherever they reach claim text or display.
- Claim `confidence` remains Gatefold's estimate of evidence support —
  independent of verification caveats and of any run's exit status.

## Limits

Per-document ceilings are unchanged and apply to `trace.json`,
`artifacts.json`, and `patch.diff` independently, plus the run-directory
ceilings in the input contract; the aggregate input is bounded by
construction. Output ceilings are unchanged: at most 50,000 emitted claims
and 100,000 total evidence references; a pair whose claims would exceed
these is rejected with `invalid-shape` before output rather than truncated.

## Errors

v0.4/v0.5 error codes are unchanged and shared. Run-directory loading adds
the input contract's cases: an unreadable directory or member is
`unreadable-file`; malformed `artifacts.json` is `invalid-json`; a bad
manifest shape, an unconfined entry path, a symlink escape, or a
non-regular artifact target is `invalid-shape`; a comparability failure is
`mismatched-inputs`; usage errors remain exit code 2.

## Representative evidence

Given two comparable runs where B's patch records a generated file A's does
not (`docs/guide.md`), a supported claim could say:

> Run B's patch records the generated file 'docs/guide.md' (12 added lines);
> run A's patch does not record it.

with evidence such as:

- `{ source: "beforePatch", pointer: "/artifacts/0",
    digest: "sha256:…", note: "no block for docs/guide.md" }`
- `{ source: "afterPatch", pointer: "/artifacts/0",
    digest: "sha256:…", path: "docs/guide.md",
    lines: { "start": 20, "end": 34 }, bytes: { "start": 700, "end": 1200 } }`

For a manifest entry whose bytes do not verify:

- `{ source: "beforeManifest", pointer: "/artifacts/0/digest" }`
- `{ source: "beforeManifest", pointer: "/artifacts/0/path",
    note: "stored bytes do not hash to the recorded digest" }`

## Contract examples (coverage requirements)

| Case | Expected behavior |
| --- | --- |
| Comparable run directories whose patches record identical file sets and content | Accepted; a summary claim states the identical generated set, and trace claims emit as in `compare-traces`. |
| File added / removed / changed between the two patches | One claim per file in path byte order; each cites `*Patch` evidence with the entry's manifest pointer, verified digest, path, and a bounded line/byte range. |
| Empty patch on both sides | Accepted; the summary claim states both patches record no files. |
| `patch.diff` listed but the file is missing | The entry's state is `missing`; a caveat claim explains the manifest records it but no file exists; no file claims. |
| `patch.diff` absent from the manifest | `patchState` is `not-recorded`; a caveat states yuurei records no patch only when generation did not succeed — never claimed as "no output". |
| Digest mismatch on `patch.diff` | `digest-mismatch`; content never interpreted; caveat claim only. |
| `truncated: true` patch cut mid-block | `verified-truncated`; the parsed prefix yields claims scoped to stored bytes; the cut tail is reported unknown. |
| Verified patch bytes that violate the grammar | `malformed`; no file claims; caveat only. |
| Manifest lists `stdout.log`/`stderr.log` | Entries preserved as `unverified`; bytes never read. |
| Malformed manifest / manifest not an object / entry missing fields | Rejected with `invalid-shape` / `invalid-json`. |
| Manifest lists the same artifact path on two entries | Rejected with `invalid-shape`; yuurei records each path once, so a repeat is contradictory, not a choice of which entry to trust. |
| Manifest entry with `..`, absolute, empty, or NUL-containing path | Run directory rejected with `invalid-shape` naming the entry. |
| `patch.diff` resolving outside the run directory via symlink | Run directory rejected with `invalid-shape`. |
| Incomparable traces (task digest, inputs_version, …) | Rejected with `mismatched-inputs` before any artifact comparison. |
| A pfl document or non-directory passed as a `--before`/`--after` argument | `unreadable-file` (not a directory) or the trace reader's codes. |
| Reordered manifest entries or patch blocks | Identical claim output. |

## Explicit exclusions

v0.6 does not add correctness, quality, or task-success judgement; `workspace/`
reading; log interpretation or inference from log text; binary or
non-patch artifact interpretation; causation between the profile variant and
output differences; or a patch application/reconstruction feature. It
describes what two matching yuurei run directories jointly record.

## Release gate

v0.6 is releasable only when:

- `pnpm ci:all` passes from a clean install;
- real-process tests cover `compare-runs` in JSON and human output,
  including incomparable traces, missing/corrupt/truncated artifacts,
  traversal attempts, and usage errors;
- every committed run-directory fixture covers its contract-example row and
  every emitted claim's evidence resolves inside the named run document and
  range;
- schema v5 is validated against a committed example and the packed tarball
  ships `claim-result.v5.json` and the v5 example;
- v0.4 `compare`, v0.5 `compare-traces`, and single-document behavior are
  unchanged;
- `npm publish --dry-run` and the installed-tarball smoke test (including
  `gatefold compare-runs`) pass;
- package and documentation versions identify v0.6.
