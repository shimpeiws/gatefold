# Gatefold v0.8 scope and run-audit contract

**Status: implemented (v0.8; issues #69–#73 under milestone #68).**
v0.8 adds a rubric-free **evidence audit** for one yuurei run directory:
`audit-run` reports which recorded facts can be mechanically checked against
the stored inputs, where records disagree, and which facts remain
unavailable. It emits fact records with stable identities — never criterion
verdicts, never a score. It builds on the
[run-directory contract](yuurei-run-contract.md) and the
[seeded-run additions](yuurei-seeded-run-contract.md), and it exists beside
the v0.7 Outcome evaluation ([v0.7 scope](v0.7-scope.md)), which is
unchanged.

## CLI surface

```text
gatefold audit-run --run <run-dir>
                   [--check-report <report.json>] ...
                   [--format human|json]
```

| Rule | Contract |
| --- | --- |
| `audit-run` inputs | `--run` names one yuurei run directory. `--check-report` is optional and repeatable; each occurrence names one external check-report JSON file whose declared subjects are audited against the run. No task spec and no criterion set is required or accepted. |
| Stdin | Directories and reports cannot arrive on stdin: `-` is rejected as a flag value with a usage error. |
| Existing forms | `gatefold <input.json>`, `gatefold -`, `compare`, `compare-traces`, `compare-runs`, `evaluate-run`, and `compare-evaluations` are unchanged — their schemas and exit codes are preserved. |
| Options / exit codes | `--format` and `--help` behave as in the existing forms. `--min-confidence` does not apply: audit facts carry no confidence. Exit codes unchanged: 0 success, 2 usage error, 3 input error, 4 internal error. |

## What an audit fact is

An audit fact is one mechanical, checkable statement about the run's stored
records — a **recorded assertion** (a field the trace or a record declares),
a **stored-byte integrity** observation (whether bytes hash to their
manifest digest), or a **cross-record consistency** check (whether two
well-formed records agree). None of these proves what the runtime actually
did; each fact says only what the records themselves support.

Every emitted fact carries:

| Field | Meaning |
| --- | --- |
| `id` | A stable, dot-separated fact identifier from the fixed list below. The set is closed; schema evolution adds IDs, never repurposes them. |
| `subject` | Present only on `check-report.*` facts: the supplied report's label, so per-report facts stay distinguishable. |
| `state` | The check outcome (below). |
| `completeness` | A **separate dimension** recording how complete the underlying evidence is: `complete`, `partial`, or `unknown`. A matching stored-byte digest does not prove a complete change set — that gap is carried here, not in `state`. |
| `reason` | A human-readable account of the state, including why a fact is `unverifiable` or `not-recorded`. |
| `evidence` | References into the named documents; every pointer resolves inside its document and every `lines`/`bytes` range lies inside verified bytes. |
| `provenance` | `{ transform: ["audit-run", "fact:<id>"] }`. |

### Fact states

| State | Meaning |
| --- | --- |
| `verified` | The records affirmatively establish the fact: digests match, declarations agree, or the declared completeness is supported by the stored bytes. A verification statement about *records*, not about runtime behavior. |
| `inconsistent` | Two well-formed records affirmatively contradict each other, or verified stored bytes violate the documented grammar/shape of the record they are stored under. The contradiction is reported, never silently resolved. |
| `unverifiable` | The fact cannot be established from what is stored: needed bytes are missing, digest-mismatched, oversized, truncated past the checkable region, or a record needed for comparison is unavailable or malformed. |
| `not-recorded` | The record the fact audits was never produced: no manifest entry, an absent optional trace field, or an absent check-report declaration. Absence is reported as absence — never as a negative or positive assertion about the run. |

### Completeness

`completeness` records whether the evidence a fact rests on is a complete
account:

| Value | When |
| --- | --- |
| `complete` | The fact is determined from complete records: whole validated documents, untruncated verified bytes, or a definitive recorded absence. |
| `partial` | The determination rests on a record that may omit content: `truncated: true` bytes, `patch.state` `"partial"`, an incomplete patch parse, or a patch-omission diagnostic on a trace that predates the `patch` record. |
| `unknown` | The record needed to gauge completeness is absent or unverifiable. Every `unverifiable` fact is `unknown`; artifact facts whose record is not stored are `unknown` too. |

### What rejects a run versus what is reported

The audit keeps the input boundary of the run-directory contract. A
violation that makes the input untrustworthy to *read* rejects the whole
run with the existing error codes (exit 3): an unreadable directory,
`trace.json`, `artifacts.json`, or check-report file; invalid JSON; a
document, entry path, or field that violates its contract shape (wrong
types, unconfined or duplicate manifest paths, symlink escapes, non-regular
targets, oversize limits). A report that cannot be *read* is an input error;
a report that is *malformed* produces `inconsistent`/`unverifiable` facts
instead, matching the v0.7 rule that a rejected report never implies a pass.

Everything else is a **bounded factual contradiction** — two records that
are each well-formed but disagree — and is included in the report as an
`inconsistent` fact rather than rejecting the run: differing requested and
materialized baseline digests, a `patch.base` that contradicts the `seed`
record, a `patch.state` that contradicts the manifest or the fixed
diagnostics, a verified `changes.json` that disagrees with `seed.changes`,
patch blocks that exceed the declared counts, or a `result:` diagnostic that
contradicts a manifest entry.

## The audited facts

The fact list is fixed and emitted in this order; `check-report.*` facts
follow once per supplied report, in argument order. Facts that have no
subject on a run (a legacy run's seeded records, an absent patch) are still
emitted as `not-recorded`, so the output shape never depends on input
content.

| Fact id | Established when `verified` | Evidence anchors |
| --- | --- | --- |
| `run.trace` | `trace.json` parses and conforms to the trace contract. (Otherwise the run is rejected.) | `trace` `""` |
| `run.manifest` | `artifacts.json` parses and conforms to the manifest contract. (Otherwise the run is rejected.) | `manifest` `""` |
| `seed.provenance` | The trace records seeded-workspace provenance (`seed`). `not-recorded` on a legacy empty-workspace run. | `trace` `/seed` or `""` |
| `seed.inputs-version` | `requested_cell.inputs_version` matches the seeded status (2 seeded, 1 legacy). `not-recorded` when `requested_cell` is absent; `inconsistent` on a contradiction. | `trace` `/requested_cell/inputs_version` |
| `seed.patch-base` | `patch.base` agrees with the `seed` record's presence. `not-recorded` on traces that predate the `patch` record. | `trace` `/patch/base`, `/seed` |
| `seed.baseline-materialization` | `seed.baseline.requested_digest` equals `materialized_digest`. This is a *declaration* check: a matching digest does not prove the baseline bytes were preserved — the baseline content is never read. | `trace` `/seed/baseline/...` |
| `seed.changes-record` | The trace records `seed.changes` (the change set is declared). `not-recorded` when absent — the change set is then **unknown**, never "no changes". | `trace` `/seed/changes` |
| `baseline-manifest.stored` | The manifest lists `baseline-manifest.json` and its stored bytes verify. Seeded runs only; `not-recorded` on a legacy run. | `manifest` `/artifacts/<n>` |
| `baseline-manifest.record` | The verified document restates the trace's seed record exactly (version, policy, source, head, digests, file inventory shape and count, total bytes). | `baselineManifest` pointers into the verified document |
| `changes.stored` | The manifest lists `changes.json` and its stored bytes verify. Seeded runs only. | `manifest` `/artifacts/<n>` |
| `changes.record` | The verified document is the v1 change record: matching `baseline_digest`, `seed.changes` recorded, and per-kind path lists matching the declared counts. A verified `changes.json` with no recorded `seed.changes` is `inconsistent`. | `changes` pointers into the verified document |
| `patch.stored` | The manifest lists `patch.diff` and its stored bytes verify. `inconsistent` on `digest-mismatch`; `unverifiable` on `missing`/`unverified`; `not-recorded` when unlisted. Completeness stays `partial` whenever the trace still records omitted patch content (a `partial` state, omission or generation-failed diagnostics, an incomplete parse) — the digest attests the stored bytes, not a complete change set. | `manifest` `/artifacts/<n>` or `""` |
| `patch.interpretable` | The verified bytes parse under the run's patch grammar (seeded baseline-relative, or legacy all-additions). Malformed verified bytes are `inconsistent`; a `patch.base`/`seed` contradiction leaves the grammar ambiguous → `unverifiable`. | `patch` manifest pointer + digest; `manifest` entry |
| `patch.record` | The trace's `patch` completeness record, the manifest entry, and the fixed patch diagnostics all agree (absent ↔ no entry, complete ↔ untruncated and no omission diagnostics, generation-failed ↔ no entry). `not-recorded` on traces that predate the record and record no patch diagnostics. | `trace` `/patch`, `/diagnostics/<n>`; `manifest` entry |
| `patch.completeness` | The stored patch is a complete change record: `patch.state` `"complete"` over verified untruncated bytes that parse fully. `"partial"`, truncation, an incomplete parse, or omission diagnostics leave it `unverifiable` with `partial` completeness; a trace with no completeness record is `unverifiable` — an untruncated patch does not *certify* coverage. `not-recorded` when no patch was published. | `trace` `/patch/state`; `manifest` entry |
| `seed.changes-patch` | The parsed patch's per-kind counts stay within the `seed.changes` declarations — exactly equal under a `complete` patch record — and a published patch never coexists with an absent `seed.changes`. | `trace` `/seed/changes`; `patch` entry |
| `changes.patch-agreement` | Every parsed patch block names a path the verified `changes.json` lists under its kind; under a `complete` patch record the per-kind sets are exactly equal. `unverifiable` when either side is unavailable — including a verified `changes.json` that is not the run's conforming change record (wrong version, a foreign `baseline_digest`, no `seed.changes`, or missing path lists). | `changes`, `patch` pointers |
| `result.stored` | The manifest lists `result.txt` and its stored bytes verify. | `manifest` `/artifacts/<n>` or `""` |
| `result.availability` | The manifest entry and the trace's fixed `result:` diagnostics agree on whether a result exists: entry present with no absence diagnostic, or no entry with the matching diagnostic. Both present is `inconsistent`; neither is `not-recorded`. | `manifest` entry; `trace` `/diagnostics/<n>` |
| `result.content` | The verified `result.txt` bytes decode to text under the contract normalization (UTF-8, one BOM, CRLF→LF). Undecodable verified bytes are `inconsistent`; a truncated or unverified entry is `unverifiable`. | `result` manifest pointer + digest + byte range |

Per supplied check report (the `subject` field carries the report label):

| Fact id | Established when `verified` |
| --- | --- |
| `check-report.shape` | The supplied document is a conforming v1 check report. A malformed document is `inconsistent`; all other facts for that report are then `unverifiable`. |
| `check-report.task-binding` | The report's required `subject.taskDigest` equals the run's `trace.task.digest`. |
| `check-report.baseline-binding` | The report's declared `subject.baselineDigest` equals the run's `seed.baseline.requested_digest`. `not-recorded` when the declaration is omitted; `inconsistent` when declared and different — including declaring a baseline on a run with no seed. |
| `check-report.patch-binding` | The report's declared `subject.patchDigest` equals the run's verified `patch.diff` manifest digest. `not-recorded` when omitted; `unverifiable` when declared but no verified patch exists to check against; `inconsistent` when the verified digest differs. |
| `check-report.results` | The report's result rows carry no conflicting duplicate `criterionId` rows. Conflicting duplicates are `inconsistent`; identical duplicates are preserved as a reported limitation in the reason. Rows are self-declared verdicts — they are never turned into pass/fail Outcome judgements. |

**Self-declaration caveat.** A matching subject digest only shows the
report *declares* it evaluated those bytes. It never attests that the
evaluator actually ran on them — Gatefold does not check execution. Agent
prose, stdout/stderr logs, and `result.txt` content never serve as an
external check report.

## Result contract: schema v8

`audit-run` emits `schema/claim-result.v8.json`:

| Field | Type | Meaning |
| --- | --- | --- |
| `schemaVersion` | integer `8` | Result schema version. |
| `source` | `{ command: "audit-run" }` | Discriminator. |
| `inputs` | object | `{ run, checkReports }`. `run` is the seeded-aware run descriptor of v6/v7 (`EvaluationRunDescriptor`); each check-report descriptor is `{ label, document: "check-report", evaluatorId, evaluatorVersion?, state, error?, resultCount }` with `state ∈ parsed | invalid`. |
| `context` | object | The observed run context (`execution`, `model`, `usage`, `cost`), kept separate from facts. |
| `facts` | array | The fixed fact list in the order above, then per-report facts in argument order. |

Evidence sources are the run's `trace`, `manifest`, verified `patch` and
`result` bytes, the verified `baselineManifest`/`changes` documents, and
each supplied `checkReport`. Pointers into `baselineManifest`/`changes`
resolve inside the artifact's parsed JSON document with `digest` repeating
the verified stored digest; `patch`/`result` keep the v6/v7 convention of
naming the artifact's manifest pointer. When an artifact's document is not
verified, evidence cites the manifest entry instead.

Deterministic ordering: facts follow the fixed list above; check-report
facts follow argument order; evidence inside a fact is sorted by source
order then pointer byte order. Output never depends on manifest entry
order, patch block order, or filesystem iteration.

## Limits

- Every document and artifact read honors the shared 16 MiB ceiling and the
  existing scalar/array bounds; nothing in `workspace/`, the source Git
  repository, or any path named inside a record is ever opened.
- The run descriptor, trace/manifest pointers, artifact byte ranges, and
  sanitization follow the same rules as v0.6/v0.7.
- Output ceilings are unchanged: at most 50,000 facts and 100,000 evidence
  references; excess is `invalid-shape`, never truncated.
- Stored-byte integrity is not authenticity: a matching digest shows the
  stored bytes are what the manifest recorded, not who produced them. A
  baseline digest declares an identity, not a preserved baseline. A declared
  check-report subject is a self-declaration, not an execution attestation.
- v0.7 criterion verdicts are never repurposed: a `verified` fact is not a
  `pass`, and no aggregate score, rubric, or Outcome verdict exists in v8.

## Contract examples (coverage requirements)

| Case | Expected facts |
| --- | --- |
| Real seeded run, all records consistent | Every fact `verified`; `seed.*`/`baseline-manifest.*`/`changes.*` facts present. |
| Legacy empty-workspace run | `seed.*`/`baseline-manifest.*`/`changes.*` `not-recorded`; `patch.completeness` `unverifiable` (no completeness record exists). |
| Seeded run, `changes` `{0,0,0}`, `patch.state` `complete`, empty `patch.diff` | `patch.completeness` and the change-set checks `verified` — a complete empty patch is distinct from an absent one. |
| `patch.state` `"absent"`, no `patch.diff` entry | `patch.stored`/`patch.interpretable`/`patch.completeness` `not-recorded`; `patch.record` `verified`. |
| `patch.state` `"partial"` or `truncated: true` | `patch.stored` `verified` with `partial` completeness; `patch.completeness` `unverifiable`; subset checks still verified against `changes.json`. |
| `patch.diff` digest-mismatch / missing / oversized | `patch.stored` `inconsistent`/`unverifiable`; dependent checks `unverifiable`; the bytes are never interpreted. |
| `requested_digest` ≠ `materialized_digest` | `seed.baseline-materialization` `inconsistent`; the run is still audited. |
| `patch.base` `"seeded"` with no `seed` | `seed.patch-base` `inconsistent`; `patch.interpretable` `unverifiable` (ambiguous grammar). |
| `changes.json` count/paths disagree with `seed.changes` or the patch | `changes.record` / `changes.patch-agreement` `inconsistent` with both documents cited. |
| Verified `changes.json` but no `seed.changes` | `changes.record` `inconsistent`. |
| Verified `baseline-manifest.json` that is not JSON / restates different fields | `baseline-manifest.record` `inconsistent`. |
| `result:` diagnostic with no manifest entry | `result.availability` `verified` (the records agree no result was stored); `result.stored`/`result.content` `not-recorded`. |
| Manifest entry *and* a `result:` absence diagnostic | `result.availability` `inconsistent`. |
| Check report matching/mismatched/omitted/malformed | `check-report.*` facts report each declaration separately; `shape` `inconsistent` on a malformed report leaves its bindings `unverifiable`. |
| Traversal path, duplicate path, symlink escape, corrupt manifest | Run rejected `invalid-shape`, exit 3 — never reported as facts. |
| Hostile text in `result.txt`, patch, or report fields | Treated as data; sanitized on display; never executed. |

## Errors

| Condition | Code | Exit |
| --- | --- | --- |
| Missing/duplicated flags, `-` where a directory is required | usage error | 2 |
| Unreadable run directory or report file | `unreadable-file` | 3 |
| `trace.json`/`artifacts.json` not valid JSON | `invalid-json` | 3 |
| Run document shape, path confinement, or limit violations | `invalid-shape` | 3 |
| Check report not valid JSON, shape-violating, or an unsupported version | reported, not rejected: an `invalid` report descriptor with `check-report.shape` `inconsistent` and its bindings `unverifiable` | 0 |

## Explicit exclusions

v0.8 does not add: a `pass`/`fail` Outcome verdict, rubric, criterion set,
aggregate score, or ranking; causal attribution; baseline reconstruction
from the source repository; `workspace/` or log content interpretation;
agent-prose fact checking; command or test execution; or a claim that a
self-declared identity is an independently attested execution.
